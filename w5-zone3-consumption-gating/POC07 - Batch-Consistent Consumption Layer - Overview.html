Point of view · Batch-consistent consumption layer

Publishing each domain only when its batch is completeA point of view on CTAS + Swap — what to keep in mind, what is proven, what the POC must prove

While the nightly batch runs, reports can show a mix of today’s and yesterday’s data. This deck sets out how CTAS + Swap would publish each domain in one step, only when its batch is complete, with its tags, masking and access rights intact — what is already proven, what the POC must still prove, and what to keep in mind. Clone + Swap is kept as a parallel thread.

Focus — CTAS + Swap  each view’s result is saved as a published table in a staging area, the tags are re-applied, then staging is swapped with live
Parallel thread — Clone + Swap  ETL loads a clone of the base tables in a staging area, then staging is swapped with live
Status  For review. Nothing run on Snowflake yet
Basis  Earlier proof-of-concept tests on our account · the design meeting summary · Snowflake documentation · 25 October 2026

1 · The problem

Mid-batch, reports mix today’s and yesterday’s data

What goes wrong, the fifteen requirements, and our initial understanding

Each night a batch loads many related tables. Partway through, some hold today’s data and others still hold yesterday’s, or have failed. Reports read them through views, so a user can see numbers that don’t add up — even though each table on its own is valid.

Initial understanding — to be confirmed Initial inputs
1. Domain: the set of related tables that must switch to new data together. What exactly a domain maps to, and its list of tables, is still to be confirmed.
2. Loads: all domains are loaded incrementally. To be confirmed in writing.

R2New data becomes visible only when all the tables it depends on have finished loading
R3The whole domain (facts and dimensions together) is consistent — never part old, part new. Across domains: out of scope unless stated
R4A batch that fails partway is not released to users
R5The business can still release a partial load, by a deliberate manual step
R6Publishing is one controlled event, not something each view works out for itself

R9Every refreshed table has the correct masking on sensitive data

2 · CTAS + Swap

Two checks guard every publish — completeness first, security always

The checks before the swap, the business override, and the shared rules

1Completeness checkevery load on the domain’s required list has succeeded for this batch; a missing load fails it
2Security check — never skippeda test row reads as real, nothing stored as hashes, tags and scope as in the tag config table, widths fit the masked value
3Publish — the swapstaging and live switched in one step
4Log every attemptpublished, refused or overridden — who, when, approver, reason

Business override: an approved person can skip check 1 to release a partial load — never check 2. The skip is logged. That the business may choose to publish a partial load comes from the design meeting.

One tag config table
Lists the expected tag for every sensitive column and the expected scope for every table. Check 2 compares against it, and the recommended tag method re-applies the tags from it.
The batch account’s approval row
The service account that writes the data has an all-access approval row; without it, it stores masked values, with no error Proven
Timings with masking on
Every timing is taken as the batch account with masking active, because masking adds a lookup for each value.

Straight after the swap, could a report see one table new and another old? That is a test for the POC (slide 10).

Nothing becomes visible until the security check passes; an override can skip only the completeness check

2 · CTAS + Swap

Our proven tagging model masks by tag, scope and a per-user approval

How the model proven earlier on our account decides what each reader sees Proven

How a value gets masked

1A report reads a column
2The column’s tag names what it holdsfor example EMAIL
3The masking rule looks up the approval tablethis user, this attribute, this table’s scope
4Match: real value · no match: masked
Tag on columns
Names what the column holds (SSN, EMAIL …). Only on columns.
Tag on schemas (scope)
Set on a database, schema or table and passed down; the nearest wins. A new table in a tagged schema is protected without its own tag.
Masking on the tag
Tag a column and its masking comes with it. The rule runs with its owner’s rights, so the approvals stay hidden from the people they govern.
Approval table
One row = one user, one attribute, one scope. Approval is per user, not per role. Service accounts get one all-access row.

What we learned to watch

  • A writer that sees masked values stores the masks, with no error — hence the batch account’s all-access row
  • Removing a table-level scope can open access
  • Masked text can come back longer than its column; a masked number that doesn’t fit fails

Controls carried forward

  • No role unmasks anything; the account administrator role isn’t used
  • A scheduled check compares tagged columns with protected columns
  • An alert fires if a scope value is removed; new scope values are added, never overwritten
Approval is per user, attribute and scope — and the model is already proven on our account

A plain CTAS drops the tags — three ways bring them back

The options, the working recommendation, and what must be tested before it is final

#OptionHowNeeds a clone?A newly tagged base columnReach

Working recommendation		After each rebuild, set each tag from the config tableNoPicked up once the config is updatedThis step only
2COPY TAGSEach rebuild keeps the tags of the table it replacesYes — live is cloned first, only to carry the tagsNot picked upThis rebuild only
3Automatic tag propagationOne setting on the tag; Snowflake copies tags as data movesNoTaken from the source columnsWhole account — affects other loads too

Why option 1 — working recommendation, to be confirmed by testing

  • The tag config table has to be kept up to date anyway, for the security check — one source of truth
  • It handles a newly tagged column, which COPY TAGS can’t do on its own
  • No clone, so live is frozen for a shorter time
  • No account-wide setting; needs only the right to apply the two tags, already proven on our account
  • Re-applying from a configuration table was an idea raised in the design meeting

To prove before it is final

  • The publishing role can set the tags with only the right to apply them
  • After re-tagging, approved readers see real values and others see masked ones
  • A newly tagged base column is tagged on the next rebuild once the config is updated, and the publish is refused until then
  • How long the re-tag step takes for the largest domain
Note on an earlier finding. Our findings register says “a refresh must clone, never rebuild with CTAS” — written because a plain CTAS loses the tags. CTAS + Swap holds only if the tags are put back before anything is visible: re-applied in step 3, then verified by the security check. That is exactly what the tests above must prove.
Working recommendation: re-apply the tags from the tag config table — to be proven before it is final

4 · The parallel thread

The parallel thread: Clone + Swap

What it is, how it differs from the meeting’s idea, and what it would need

1Clone every base table to stagingthe clone is the new data; it keeps the tags
2ETL loads staging, not liveevery read and every write — the normal incremental load
3Check every load finishedthe same completeness check
4Check security in stagingthe same security check
5Swap staging and live SWAPthe existing views now read today’s data

How it differs from the meeting’s idea

In the meeting, Clone/Swap meant cloning physical consumption tables — which would mean turning many existing views into ETL-built tables.

This analysis’s version clones the base tables instead: ETL loads the clone, and the existing views stay exactly as they are.

What it needs to work

  • Every ETL read and write points to staging, including lookups and jobs that read their own table — a job still reading live gets yesterday’s data, and the checks would not catch it
  • No job drops and re-creates its table: the new table has no tags (proven)
  • The domain’s tables sit in one schema, not shared; views sit outside it and name their tables in full
  • Live stays frozen from the clone to the swap; change feeds on base tables break at each clone

Still to check: to confirm with the team — whether every job can point to staging, and today’s table layout and view names. To prove in the POC — a job that reads its own table reads staging, not live.

Clone + Swap keeps the views and the tags — but every ETL read and write must move to staging
