Zone 3 consumption gating

While a batch is running, a reporting user can read a dataset that was never a valid version — part of this cycle's load against part of the previous cycle's. Every source object is individually correct, so nothing flags it. The requirement is to put a boundary between loaded and visible: data becomes visible as a controlled publication event, not as a side effect of loading.

What the consumption layer must guarantee

Two guarantees, delivered together: what a reporting user is shown, and whether it is still protected.
Part AWhat a reporting user is shown
1
One version, or none
A report shows a complete version of every object it depends on — never a partial one, never a mixture of two cycles.
2
Publication is a decision, not a consequence
Data becomes visible only when publication runs, after every job in the cycle has succeeded. A failed cycle publishes nothing: reporting users stay on the previous version until the next successful publication, with no timed auto-release. The business can still authorise a release, on the record.
3
What is published is the real data
Masking acts on the read, by role — storage stays plaintext. But publication copies, and a copy reads before it writes: if the publishing identity may not see real values, masked values land on disk permanently.
Part BWhether it is still protected
1
Protection travels with the data
A republished object carries the tags, masking and access currently defined for it — including every change governance has made, and never reinstating one it has removed.
2
Protection lands before anyone can read it
The governance step sits inside the publication gate, not after it.
Binding on both. It has to work on the estate we have: repeatable every cycle, run by the batch identity, and achievable without rewriting existing view logic as new ETL.
Correct data, and protection that survives the publishing of it — neither guarantee is worth much without the other.

What gets gated, and what comes along for free

A consumption object is a table or a view. One holds a version of the data; the other holds none — and that single difference decides the treatment and the cost.
Back to the 04:10 report. It reads a view, and the view reads twelve tables. Gate the twelve tables and the report is correct — the view itself is never touched, and needs no change at all. That is the common case.
Which makes the cost question "how many tables", not "how many views". The estate has thousands of views; the number of tables under the reports that matter is a far smaller number, and nobody has measured it yet.

The exception, and it is where the effort sits. A view whose tables span two different groups, or which is itself the frozen contract a report points at, cannot simply inherit — it has to become a table of its own, and the view is then rewritten as a single line reading that table, so its name and its consumers are unaffected. How many fall into that category is one of the two things the sizing walk answers.

Tables hold the version; views inherit it. Gate the tables and most of the view estate is fixed without being opened.

Why the last row matters. The requirement makes publication a decision. Anything that refreshes and reveals in one managed step turns it back into a consequence.

We need one refresh mechanism and one publication mechanism. The next two slides compare the candidates for each and land on one of each.
A view is not a layer. A view holds no data, so it cannot be gated directly — it is consistent only when the tables beneath it are. That makes the view estate a beneficiary of gating, never a site of it, and it is why the cost question is “how many tables”, not “how many views”.
Two decisions, not one: how the data lands, and how it becomes visible. Each is settled on its own evidence.

How a consistency group is derived

Computed from the dependency graph — never chosen object by object, which is the only way this holds at estate scale.

The problem a transaction’s freedom creates

A transaction can publish any set of tables. So groups need no longer match a schema — but nothing then stops two groups sharing an object, and a shared object is published once for everyone.
#If a shared dimension sits in two groups
1Group 1 publishes at 02:00 — the new dimension becomes visible to everyone
2Group 2's facts load until 05:00. For three hours it reads a new dimension against old facts  the defect
3Group 2 publishes. Consistent again — and nobody was told

An object has one visible state, so publishing it is a global act even when the decision was local to one group.

The answer: let the graph decide

Treat reports and objects as a graph. A consistency group is a connected component of it — if two reports share an object they are one group, because the graph says so, not because anyone judged it.

Every object lands in exactly one group by construction, so overlap cannot occur and the requirement is satisfied without a single per-object decision.

What that costs, and the one rule

Honest group sizesIf a date dimension touches everything, the component is the estate. Publishing it together is the true cost of “never a mixed state”
Too large?Break connectivity by rule — a named schema, tag or convention marking a class ungated. One line of config, applying to every object past and future
NeverObject-by-object adjudication. That is a backlog, not a design

It is the sizing walk with one more step, re-run on every deployment — so a new view bridging two groups is caught by the pipeline, not by someone noticing.

Groups are computed, not chosen — and that is what keeps non-interference true as the estate changes.

What we must prove before concluding this POC

Nothing here is a decision yet. Five tests can still change the design; the rest confirm documented behaviour on our account.

The five that can change the design

QuestionIf it fails
Does insert overwrite preserve tags, masking and OWNER? Grants are documented; these are notInsert overwrite collapses toward CTAS, and the per-cycle ownership problem returns
Does a reader spanning the commit ever see a mixed state? Follows from READ COMMITTED, but it is the single most important claim hereThe transaction is out, and the schema constraint returns with the swap
Is a governance-removed tag reinstated by a publish? Part B's non-reinstatement clauseThe gate’s governance step becomes mandatory, not advisory
Is stored data plaintext under a masking policy? Undocumented; inferred from read-time enforcementIf storage were masked on write, losing a tag would be harmless — and Part B would not need to exist
Do consistency groups fit inside one schema? Offline, read-only, runnable todayA schema swap cannot publish those groups — the transaction becomes the only route

Still open — and not ours to close

May the batch identity read sensitive data in the clear? Physicalizing reads the data, so this sets how much can be gated at allSecurity
Is there a declared governance baseline? Without one, “never reinstate a removed protection” cannot be implementedSecurity
Can the batch identity publish? A transaction needs INSERT and DELETE; a schema swap needs OWNERSHIP on both schemasPlatform
