What the refresh had to guarantee

The requirements the POC set out to prove — the third is the hard one

#RequirementIn plain terms
1Shrink the windowThe time a reader can be exposed to a changing table approaches zero
2Never a partial stateA reader sees version N, then N+1 — never a mix, never an empty table mid-load
3Related tables agreeWhen a set must be consistent (parent + child), no reader sees a new parent against old children
4Masking not weakened, not baked inColumns stay protected through the cutover, and the pipeline never writes masked values as real data
5A bad load can be stoppedA corrupted or mis-tagged load can be refused before any user sees it
6The masking layer is untouchedThe existing governance objects are reused read-only — nothing disturbed
Why requirement 4 is the hard one. A masking rule applies to every identity not approved — including the one that owns the table. A pipeline denied real values does not stop; it reads masked values and writes those to disk instead. Both refresh strategies have to design around that.
Six requirements. The masking one is where the design earns its keep.

Two strategies, three ways to cut over

Clone-and-swap — with a single-table and a whole-schema variant — versus a dynamic table

STRATEGY 1 — CLONE-AND-SWAP
Clone it, load the clone, swap it in

Readers stay on the live table. A clone is made, the pipeline loads it, a gate checks it, then the two exchange names in one atomic transaction.

Single-table swap — one table at a time.

Whole-schema swap — a related set (parent + child) flips together, atomically.

Keeps: a checkpoint to reject a bad load. Costs: cutover code to maintain.

STRATEGY 2 — DYNAMIC TABLE
Let Snowflake hold the table

The presentation table becomes a dynamic table on a freshness target. Snowflake decides when to refresh it and makes the result visible atomically.

Keeps: no cutover code; a coordinated view across a set.

Costs: no point at which anything can be checked before readers see it; a plaintext copy at rest; full rebuild every cycle over a masked base.

One keeps a checkpoint and costs you code. The other removes the code — and the checkpoint with it.

The governance point that decides it

Nothing is masked at rest — so the real question is how protection is applied

The myth. "A clone is masked at rest; a dynamic table is not." False — and a draft of the pack got it wrong. We proved it: remove the policy binding and the stored SSN reads back as 111-22-3333 on the base, a clone and a dynamic table. Tag-based masking is a read-time transform; storage is always plaintext.
The real asymmetry — protection lineage. A clone inherits the tags and policy automatically and is zero-copy: no new copy, no manual step, no unprotected window. A dynamic table is a new physical plaintext copy whose protection must be re-applied by hand to its own columns — miss it, or drop the tag later, and it is exposed with no error.
For PIIClone-and-swapDynamic table
New plaintext copy?No — zero-copy over the base's storageYes — a second physical copy
Protection applied…Automatically, inherited with the cloneBy hand, on the copy's own columns
Extra exposure surfaceNoneIts own Time Travel, Fail-safe, share / replication
Clone-and-swap adds no new plaintext copy and inherits protection. That is the strongest reason to prefer it for PII.

The recommendation

Clone-and-swap as the default — three reasons, each backed by a captured result

Clone-and-swap is the recommended default. A single-table swap for one table; a whole-schema swap when related tables must stay consistent. Use a dynamic table only for a single-SELECT feed where a plaintext copy at rest and full-rebuild cost are acceptable.

Recommended flow — readers never touch the table being loaded

Clone-and-swap, end to end — who holds what, and when the cutover happens

#StepWhy it is done this way
1Clone into the same schema, with grantsA clone elsewhere loses inherited protection; grants are not copied unless asked
2Pipeline loads the cloneIt holds an approval row, so it reads real values and cannot write masked ones
3Tag anything newA new column carries no tag, so it is unprotected until tagged — nothing errors
4–5Gate, then swapThe gate is the only point a bad load can still be refused; the swap is the whole visible window
6Keep, then dropThe old version waits one cycle, so rollback is another swap
Everything expensive happens where nobody is looking. Only the swap is visible.

Related tables — a whole-schema swap flips the set together

One atomic ALTER SCHEMA … SWAP WITH, so no reader sees a new parent against old children

#StepWhat it guarantees
1–2One ALTER SCHEMA … SWAP WITHBoth schemas — parent and child together — exchange names, grants and tags in a single transaction. The scope tag follows the schema (verified)
3A reader spanning the swapSees a whole consistent set before, a whole consistent set after — never a new parent against old children
Know before you go. A view that names a table by its full old-schema path breaks after the swap. Use unqualified references, or refresh views post-swap.
Schema swap is the multi-table cutover — set-consistency and the gate, in one atomic rename.

When a dynamic table is the right choice

The narrow case it still wins — and the questions that point you there

#If this is true……then
1The load is procedural, a gate matters, related tables must agree, or cost must be windowedClone-and-swap — the default
2The transform is a single SELECT, freshness beats control, and a plaintext copy + full-rebuild cost are acceptableDynamic table — the narrow case
Honest framing. A dynamic table is not wrong — it is a platform commitment rather than a piece of code: monitor refresh state, and remember a masking-rule edit rebuilds it. It simply loses on the three reasons that matter most for PII presentation tables.
Default to clone-and-swap. Reach for a dynamic table only when none of the deciding questions applies.

Where this leaves us

Clone-and-swap, proven and recommended

The masking model is untouched and proven to survive a clone, a swap, a schema swap and a dynamic table. Clone-and-swap keeps a plaintext copy off disk, keeps a gate that stops a bad load, and keeps refresh cost in a window — the three reasons a dynamic table cannot match for PII tables.
