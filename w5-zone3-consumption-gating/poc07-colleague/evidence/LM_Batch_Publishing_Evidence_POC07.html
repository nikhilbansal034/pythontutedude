What needs attention

TC-04.3 — Does COPY GRANTS keep them? FAIL
S04 — Grants: swap, plain CTAS, COPY GRANTS, ownership · design test T41
  • sec-1 tags on D_STAGE.CUSTOMER_360: 0 rows, expected 2
This is the design's central correctness finding, reproduced from a different direction — not a defect in the run. TC-04.2 immediately before it does a plain CREATE OR REPLACE, which strips the tags. TC-04.3 then rebuilds with COPY TAGS — and copies from the untagged table the previous case left behind, so the tags do not come back. The grants half of this case passes; the tags half cannot. That is exactly section 2.4 row 22 and test T40 of the design: COPY TAGS takes its tags from the table it replaces, so once they are gone a rebuild cannot restore them — only re-tagging can. The case's own expectation of 2 rows assumed otherwise.
TC-04.5 — The grant bootstrap FAIL
S04 — Grants: swap, plain CTAS, COPY GRANTS, ownership · design test T41
  • TC-04.5 grants on a first build with COPY GRANTS: 2 P7_ grants present: ['P7_PUBLISH_ROLE', 'P7_VIEW_OWNER']
The case's premise is contradicted by its own evidence. It asserts that on a first build there is nothing for COPY GRANTS to copy, so “grants must be deployed too”. But the SELECT is there — supplied by the future grant in the scenario's own reset block. So future grants do cover the day-1 bootstrap that COPY GRANTS alone cannot. That is direct evidence for the design's D24 and T41, and it supports the design's choice of future grants over the COPY GRANTS route this suite relies on. Separately, OWNERSHIP is itself a grant, so “no P7_ grants” can never be literally true.

What the harness did that the SQL does not say

Stated so the deck never implies the files did something they do not. The runner injected 762 statements across all runs, two kinds only, both after every USE ROLE:

  • USE SECONDARY ROLES NONE — the files set this once at the top, but a USE ROLE re-enables the account default. This operator's account carries POC01's LM_PII_TAG_ADMIN and LM_PII_POLICY_ADMIN as active secondary roles, so without it a privilege check could pass through a role other than the one under test. That is the flaw that produced POC02's retracted P2-F1 finding.
  • USE WAREHOUSE LM_PII_POC_WH — no scenario file issues this, so after switching to a P7_* role the session would still point at the connection's default warehouse, which no P7_* role can use. Every query would fail on that rather than on anything being tested. It is best-effort: SECURITYADMIN and SYSADMIN hold no grant on the warehouse and need none for DDL, so a failure there is recorded and ignored.

What this run does not prove

#LimitationWhy it matters
1No gate is enforced. This suite has no stored procedure by design — every gate is a SELECT a human reads before running the next statement by hand.Nothing stops an operator reading "2 rows returned" and swapping anyway. The design's owner's-rights questions (T11, T12) cannot be answered without a procedure, and T12 is graded the most important test in the design.
2Identity is a role switch, not a service principal. 00_setup.sql creates no users, so every step runs as this operator switching role.Weaker evidence than POC01/POC02, which used a key-pair per user. A role switch by someone who could reach the privilege another way proves less than a login that holds only that role — mitigated, not removed, by USE SECONDARY ROLES NONE after every switch.
3Masking is one STRING policy keyed on CURRENT_ROLE().POC01's proven model is three typed policies keyed on CURRENT_USER(), attribute and scope. The masking here exercises the mechanism, not the model that is actually in production.
4No tag configuration table, so no mapping check.The design's config-against-base and source-mapping checks (section 3 row 2) have no counterpart. Those are what would catch T32.
5Seven setup grants run as ACCOUNTADMIN.The suite's header claims no ACCOUNTADMIN anywhere, and that holds for every test statement. It does not hold for the seven GRANT USAGE ON WAREHOUSE statements: the warehouse is owned by ACCOUNTADMIN and SYSADMIN holds no grant on it. Stated rather than quietly done.
6Volume is trivial. 20 customers, 50 policies.Nothing here says anything about the batch window at real volume — the design's Q5 timing question is untouched.
7The suite publishes unprotected PII on purpose. s03 TC-03.1 publishes four times with no security check at all.Intentional, on synthetic generated data in an isolated database. Worth knowing before anyone reads the publish log as a real exposure.

Where the SQL had to be corrected before it would run

The suite had not been run before. Seven defects prevented it; each is recorded with its evidence in Nikhil - 2/CHANGES.md. The substantive ones: a warehouse that does not exist on this account; seven warehouse grants run as a role that cannot make them; two future grants run as a schema owner, which Snowflake requires MANAGE GRANTS for; 58 unqualified grants that fail because USE ROLE SECURITYADMIN drops the database context; and 44 tag checks that never filtered to the PII attribute tag, so an inherited schema-level PII_SCOPE made every one of them return the wrong row count. None of these changed what is being tested.
