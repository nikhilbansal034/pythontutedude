Put the region in the key when the key is minted — and give it a fixed width

Every region mints its own 1, 2, 3…, so a key qualified later no longer matches what Zone 2 stored. A reusable function combines the region code with seq.NEXTVAL at creation. How it combines them is the whole design question — and the answer is a fixed-width region field.

Why the prefix cannot wait until consolidation

Each table has its own sequence, and each region runs its own copy — so every region issues the same low integers

The mechanism of the failure

Today — Zone 2, per region, in isolation
NA EMPLOYEE_SEQ
1, 2, 3
EU EMPLOYEE_SEQ
1, 2, 3
Valid each key is unique inside its own Zone 2
On consolidation into the global database
The same integer
1
issued by every region
× N
Collision qualify it here and the global id stops matching what Zone 2 stored
So the key is qualified on the left-hand side, Zone 1 → Zone 2, and never changes afterwards — tracing a record back needs no UUID and no prefix-stripping.

Source: transcript §3 — placement attributed to Cindy MacFarlane’s preference, stated once and not revisited. D4 confirmed directly by Nikhil.

The prefix carries uniqueness, not just traceability — which makes how it is composed a correctness question, not a formatting preference.

How a key gets built — and the one step that is in question

Steps 1 and 2 are settled and proven. Step 3 is the entire scheme decision

STEP 1
Resolve the region
The region name arrives from IDMC. The function looks its code up in a mapping table.
‘North America’ → 1
STEP 2
Draw a sequence value
A Snowflake sequence, one per table per region, called by its full name inside the function body.
emp_seq.NEXTVAL → 42
STEP 3
Combine the two
The scheme. Two ways to join a region code to a sequence value — and they are not equivalent.
1 + 42 → ?
STEP 4
Cast to the target
Cast at the call site, to whatever that table’s key column is — which is not always NUMBER.
→ NUMBER(38,0) | VARCHAR

Where this happens — one line, one place

Q2, line 50 — the only place in either query that mints a key:
CAST(CASE WHEN stg.CHANGE_FLAG = '0'
     THEN …EMPLOYEE_SEQ.NEXTVAL
     ELSE stg.EMPLOYEE_ID END AS NUMBER(38,0))

Q1 leaves the key NULL for new rows. Confirmed with Nidwika (C4): the key stays in Q2, where the row’s fate is already known — C4 closed

The question step 3 has to answer

A key is one run of digits. Nothing inside it marks where the region ends and the sequence begins.

So the two parts can only be told apart if one of them has a known, constant length. That single sentence decides between the two schemes — and everything on the next three slides follows from it.

Settled: step 1 (D2, C5) · step 2 (R3, R8, R10, R12) · step 4 (R6, Q3). Open until slide 6: step 3.

Three of the four steps are proven; the scheme choice is entirely about step 3, and it reduces to one question — does either field have a constant length?

Scheme A — digit concatenation

Treat both parts as text and glue them together. Read the region back by taking the first character

How it works

region code1
sequence42
→ “142” → 142
  1. Region code to text — 1 → "1"
  2. Sequence value to text — 42 → "42"
  3. Join them — "1" || "42" = "142"
  4. Decode by taking the first character
It works today. With codes 1, 2, 3 the region always occupies exactly one character, so “first character” is always right. It works by accident of the current data — nothing in the design holds the region to one digit.

Where the boundary is lost

region 1111
sequence1
→ 111
region 11
sequence11
→ 111
Two employees, two regions, one primary key
The join point moved and nothing recorded it. Asked which region issued 111, the first-character rule answers 1 — wrong half the time.
And it collides with the keys already there
The very first key Scheme A ever mints is region 1, sequence 1 → "11" → 11 — already an existing EMPLOYEE_ID. This happens with one region. It is not about region count at all.

The real reason, stated once: the region field has no fixed width. Not “because it uses text” — see slide 7.

Scheme A is not wrong because it uses text — it is wrong because the region field’s length is allowed to vary, which destroys the boundary between the key’s two parts.

Scheme B — fixed-width offset  chosen · D5

Reserve a fixed number of digit positions for the sequence, and put the region code above them by arithmetic

How it works

region code × 10151
15 reserved positions000000000000
sequence042
region_code * 1000000000000000 + seq.NEXTVAL  →  1000000000000042
  1. Multiply the region code by 1015 — this reserves the bottom 15 digits
  2. Add the sequence value into that reserved space
  3. Decode with FLOOR(key / 1015) — arithmetic, not string position
Capacity
1015 keys per region — a quadrillion. Region codes to 1023 still fit inside NUMBER(38,0). Width is not a practical limit.

The same case that broke Scheme A

region 1111
+ sequence 1…001
→ 11000000000000001
region 11
+ sequence 11…011
→ 1000000000000011
Distinct keys, and each decodes correctly
The sequence field is always 15 positions wide, so the boundary never moves. The region can grow to any number of digits without touching it.
And it starts above the legacy range
The smallest key B can produce is 1015+1 — sixteen digits, far above every legacy EMPLOYEE_ID. No overlap to engineer around.

Proven in Snowflake: R12 run 3 — 30,000 keys, three regions, three measured-concurrent sessions, 0 duplicates. C5 v2 — two live deployments, 0 cross-region collisions.

Fixed width makes the boundary a property of the construction rather than of the current data — which is why B keeps working when the data changes.

Decision — D5
Scheme B, fixed-width offset, sequence field 15 digits. A’s two conditional passes rest on one assumption — codes stay single-digit — and rows 3 and 4 fail regardless of it. B satisfies all six with no assumption and no added control.
Stated fairly: A wins one thing — no leading zeros, so it round-trips through NUMBER losslessly where a padded scheme does not. Slide 7 shows B inherits that too.
A’s best case needs an assumption to hold forever and two controls nothing enforces; B needs neither — and A still fails rows 3 and 4 even if the assumption holds.

When the target column is VARCHAR

Q3 — the key column is not always NUMBER(38,0). The scheme does not change; only the cast does

The answer: one expression, cast at the call site

CAST(key_b(:region) AS NUMBER(38,0))  -- numeric target
CAST(key_b(:region) AS VARCHAR(20))   -- text target

The same arithmetic serves both column types, so the scheme is chosen once for the platform and only the cast varies per table — sitting in Q2 beside the 27 casts that query already performs.

Why the cast cannot move inside the function. A UDF’s return type is declared, and the target type cannot be a parameter — IDENTIFIER() accepts a literal, session variable or bind, never an argument. The alternative is one function per base type, which duplicates the guard logic. R6 Q3
And the declared length is ignored. RETURNS VARCHAR(17) is accepted, then the length is discarded — Snowflake enforces the base type at CREATE only. So the width is enforced by the target column: VARCHAR(20) covers every value a sequence can produce. R6 proven

What a text column changes — and for whom

In a VARCHAR columnAB
Sorts in issue order — "110" < "19" under A, so MAX is not the newest key and WHERE key > :last_max silently skips rowsnoyes
Constant width — A runs 2 to 20 characters with the value; B is 16 for a one-digit codenoyes
Round-trips through NUMBER — no leading zeros to loseyesyes

Considered and set aside

Scheme C — zero-padded concatenation. LPAD(code,2) || LPAD(nextval,15). It is fixed width, so it is correct — it is B’s principle expressed as text, and it was a genuine candidate.

Not chosen because the padding does not survive a NUMBER round trip: '01…042'::NUMBER::VARCHAR comes back without the leading zero, and LEFT(key,2) then reads 10 instead of 01. With a text key here and a numeric FK on a child table, that is a decode defect B simply does not have.
A VARCHAR target changes the cast, not the scheme — and it is the one case where A’s variable width causes silently missing rows rather than a visible collision.

What each number actually is

 Reading it

Each figure is an exhaustive count of a condition the mechanism predicts, on a population chosen to make that condition reachable — not a measure of how often this would happen in production.

The build standard

Every rule below is a finding from a run, not a preference — each one is there because something failed without it

CREATE OR REPLACE FUNCTION key_b(region_name VARCHAR)
RETURNS NUMBER(38,0) VOLATILE AS $$
  (SELECT m.REGION_CODE FROM region_map m
   WHERE UPPER(TRIM(m.REGION_NAME)) = UPPER(TRIM(region_name))
     AND UPPER(TRIM(m.REGION_NAME)) = UPPER(TRIM(
       (this deployment’s declared region, from config) )))
  * 1000000000000000
  + LM_DB.<home_schema>.emp_seq.NEXTVAL
$$;

The second condition is the deployment guard

It requires the caller’s region to match the one this deployment declares — so an NA deployment cannot mint an EU key even when handed a valid EU name. Proven at two-deployment scale, C5 v2.

Two consequences to accept, not work around. A wrong-region call aborts the whole DML statement, not the row. And one deployment mints for exactly one region — confirm that matches the IDMC topology.

Six rules, each with the finding behind it

#RuleBecause
1Sequence by full FQN inside the function bodyUnqualified sequences re-resolve against the caller’s schema, unlike tables — the docs promise otherwise.
2CREATE the function while in its home schemaUnqualified table references bind permanently, at CREATE time, to the session’s schema.
3Target key column NOT NULL — no exceptionsIt turns the guard’s NULL into a rejected load. Without it the row lands with no key.
4UPPER(TRIM(…)) on both sides of the guardMatching was case-sensitive — ‘NORTH AMERICA’ returned NULL. TRIM also closes whitespace.
5VOLATILE, never IMMUTABLE or MEMOIZABLEA cached key is a duplicate key. MEMOIZABLE stays prohibited rather than characterised — its doc page 404s.
6Cast at the call site, not inside the functionThe return type cannot be a parameter, so one function serves every target type.
The function is a few lines of arithmetic — everything else here exists because a run showed what happens without it.
