G1 — Function interface & contract

R1 call site · R2 signature · R6 return type — the call site is fine, the other two need a workaround

IDRequirementWhat Snowflake documentation saysStatus
R1 ETL calls a reusable function instead of <seq>.NEXTVAL “A SQL UDF evaluates an arbitrary SQL expression.” Nothing restricts calling a scalar UDF in a MERGE … USING projection.Reads as: the call site is not the problem. R1 inherits whatever R3 needs. Closedpending R3
R2 Signature takes region name and sequence name “Dynamic SQL is not supported when referring to database objects.” The docs’ failing example is this exact pattern — a UDF taking an object name as VARCHAR via IDENTIFIER(param). IDENTIFIER() accepts only a literal, session, bind or Scripting variable.Reads as: the name cannot be resolved as an identifier — but it can be compared as a value. Workaround
R6 Returns the target’s datatype; cast inside the function “the received value may be used as received whether or not it conforms to constraints specified in the declaration.” Ignored for SQL UDFs: “Precision and scale for … NUMBER”.Reads as: RETURNS NUMBER(38,0) is documentation, not enforcement — the body must cast. Workaround
R2 workaround — the name selects a branch. CASE sequence_name WHEN 'EMPLOYEE_SEQ' THEN EMPLOYEE_SEQ.NEXTVAL … END. Cost: the function must know every sequence by name, so onboarding a table edits the function — still one place, but not the generic thing the signature implies.
Asked: can a registry table hold the full sequence name? No, not inside a UDF. The blocker is not where the string comes from — no run-time value can become an object reference. DuckDB refuses it identically: “must be a constant expression”. Two shapes that do work: generate the function from the registry, or use a stored procedure via TABLE(proc(…)).

Sources: SQL UDF limitations · IDENTIFIER() syntax · Introduction to SQL UDFs — read directly. Qualified names: they work, but hard-code db/schema and so break R8 — prefer unqualified.

The signature survives, but only because the sequence name can pick a branch rather than name an object — and the return type must be cast in the body, because the declaration is ignored.

G2 — Sequence access: the one blocker

R3 — may a SQL UDF body contain seq.NEXTVAL? The documentation does not say, either way

What the documentation says — nothing

Page checkedMentions sequences?
CREATE FUNCTIONNo
Introduction to SQL UDFsNo
SQL UDF limitationsNo
Using SequencesNever mentions UDFs
The one adjacent rule does not settle it. “DDL and DML operations are not supported in UDFs” — but consuming a sequence is neither DDL nor DML. Not prohibited, not permitted.
DuckDB cannot answer this, and would mislead. DuckDB’s nextval('name') takes a string; Snowflake’s seq.NEXTVAL is an identifier. So a wrapper function succeeds in DuckDB and proves nothing. That false positive is demonstrated deliberately in explore/r2_sequence_name_binding.py §1 so it is never mistaken for evidence.

Three outcomes, and one is a trap

Result of the testConsequence
CREATE failsR3 impossible in a SQL UDF. R2’s signature cannot hold with NEXTVAL inside. Fall back.
10 distinct valuesR3 achieved The branch-selector design is viable. Proceed.
10 identical valuesWorst case — silent The body was folded to a constant. R3 unusable, but no error is raised. This is why CREATE succeeding is not enough.

Fallbacks, in order

  1. Pass the value in — f(region_name, seq_value), NEXTVAL stays in the query. Loses half of R2; keeps everything else.
  2. Stored procedure via TABLE(proc(…)) in the MERGE source. Docs permit this for MERGE — open question is whether consuming a sequence counts as a “modification”.
R3 is the base of everything else and no amount of further reading will settle it — it needs one statement run in a Snowflake account, and a pass that returns identical values is a failure wearing a success.

G4 — Key composition & integrity

R5 combine · R12 uniqueness · R13 decodable — one decision closes all three, and it is a decision, not a test

The two candidate schemes, measured

PropertyDigit concatFixed-width offset

Why concatenation fails. concat(1, 23) and concat(12, 3) are both 123. Collision-free today only because the three allocated codes are single digits — it breaks at a tenth region, with no error raised.

Measured: explore/prefix_schemes.py — 4,389 keys, 11 regions, on DECIMAL(38,0).

Recommendation — fixed-width offset. The only scheme meeting R12 and R13 unconditionally, and it removes §4’s datatype problem rather than centralising it. Pin the field width with the decision — changing it later renumbers every key ever issued.
IDRequirement & what the docs say
R5Combine region code with sequence value. No constraint on the arithmetic; a sequence value is a 64-bit integer and exceeding that range fails the query.Reads as: “combine” is underspecified — the two readings behave very differently.
R12Unique across regions, for all time. “All values generated by a sequence are globally unique” covers one sequence. Per D4 each table has its own per region, so the prefix is the separator — Snowflake guarantees the sequence half, the composed key is a scheme property.
R13Region recoverable without a join. Not a Snowflake question.Reads as: offset decodes by key / 10^n and key % 10^n. Concatenation gets the region from the first character only, and never the sequence value.
With one sequence per table per region, the prefix is the only thing separating two regions’ primary keys — so concatenation’s failure at a two-digit region code stops being untidiness and becomes a correctness loss.

The real hazard: volatility, not concurrency

Every row passes this function identical arguments — same region name, same sequence name, all statement long. On IMMUTABLE: “UDF assumes that the function, when called with the same inputs, will always return the same result. This guarantee is not checked. Specifying IMMUTABLE for a UDF that returns different values for the same input will result in undefined behavior.” Default is VOLATILE.
So IMMUTABLE invites one surrogate key for every new row, silently — and MEMOIZABLE is the same failure by another route. Build rule: declare VOLATILE explicitly with a comment saying why, never the other two, and assert N rows receive N distinct keys.
Snowflake already guarantees the concurrency the action item asked about; the residual risk is a single keyword that would silently collapse every new key to one value.

How each outcome reshapes the design

2, 3 and 6 all passR3 achieved The branch-selector design is viable. G1 and G5 POCs proceed as written.

What is needed to run it

  1. A scratch database and schema — nothing in the script touches real objects, and it ends with a teardown.
  2. Privileges to CREATE SEQUENCE, CREATE FUNCTION and CREATE TABLE in that schema.
  3. Record each result. Do not infer one test’s outcome from another — the silent case looks like success.
A second, smaller unknown rides along. If the fallback is needed: does consuming a sequence count as “making modifications using DDL or DML operations” for TABLE(proc(…)) eligibility? Undocumented — another short test, worth the same session.
R3 is cheap to answer and expensive to assume — one scratch schema and under a minute decides whether the frozen signature is buildable at all.
