POC05 — same-name clone refresh for consumption

Recreating the clone on Day 2 —
do users or reports break?

A consumption object is a clone of a Zone 3 intermittent table, recreated daily under the same name so reports keep a stable object to point at. This deck answers whether the Day-2 recreate affects anyone reading the Day-1 clone.

Short answer  Safe for concurrency — Snowflake guarantees old-or-new. The one real risk is grant loss, fixed by COPY GRANTS.
Basis  Verified against current Snowflake documentation (CREATE TABLE / DROP TABLE, cloning-privileges KB). Same class of problem as POC02.
Discipline  Synthetic data only; read-only and additive on existing objects.

The Day-2 recreate

Three effects — only one is a real risk

Concurrency is guaranteed safe; grants are the trap; downstream is conditional.

1 — Access the one to watch

CREATE OR REPLACE…CLONE = DROP + CREATE. The recreated object keeps only OWNERSHIP — every explicit SELECT to reporting roles is lost. Reports then fail with “does not exist or not authorized” on the next run — it does not error during the reclone, so it is easy to miss.

-- fix: copy grants in the same statement
CREATE OR REPLACE TABLE ZONE3_CONSUME
  CLONE ZONE3_INTERMITTENT
  COPY GRANTS;

2 — Concurrency not an issue

CREATE OR REPLACE is atomic: any concurrent query uses either the old or the new version. A query in flight completes on the Day-1 snapshot; one starting after sees Day-2. No missing-object window, no torn read.

Subtlety: one report firing several queries straddling the exact recreate instant could see v1 in one and v2 in another (each internally consistent). Reclone in a quiet window if a report needs one snapshot across queries.

3 — Downstream & storage conditional

Streams go stale — recreating drops the change data (matters only if something consumes CDC off the clone). Time Travel storage accrues — each OR REPLACE retains the prior version; set DATA_RETENTION_TIME_IN_DAYS to bound it.

Order it right. A clone snapshots committed data — finish and commit the source load before recreating, or the clone captures a partial state.

The Day-2 recreate

Where COPY GRANTS takes the grants from

The docs are explicit — and the first-creation case is different from steady state.

Docs: if the statement replaces an existing table of that name, grants are copied from the table being replaced; if no table of that name exists, they are copied from the clone source.
#DaySituationCOPY GRANTS copies fromConsequence
1Day 2+
steady state		ZONE3_CONSUME already existsthe replaced ZONE3_CONSUMEWorks reporting roles’ SELECT is preserved
2Day 1
first creation		no ZONE3_CONSUME yetthe clone source (ZONE3_INTERMITTENT)Gap roles usually have SELECT on the consumption object, not the raw source — so Day 1 may give them nothing

Handle the Day-1 bootstrap

AAfter the first creation, grant the reporting roles once explicitly. From Day 2 on, COPY GRANTS carries them forward.
BOr use future grants on the schema — covers Day 1 and every day with no bootstrap step.

Two models — pick one

They are mutually exclusive per statement: with COPY GRANTS the new object gets the explicit grants but not future grants; without it, it gets future grants but not the previous explicit ones. The future-grants model removes the bootstrap entirely — a point in its favour.

Verdict

Does the Day-2 recreate affect users?

It depends entirely on whether grants are handled — nothing else.

PathResult for users / reports on Day 2
Naive CREATE OR REPLACE…CLONE avoid
(no grant handling)		Reports lose access after the reclone — the failure mode to avoid.
…CLONE…COPY GRANTS (or future grants) recommended
+ no downstream stream		No issue — in-flight queries are safe, access is preserved, users simply see refreshed Day-2 data on their next query.
The thing to test explicitly is grant survival across the same-name reclone — not query concurrency, which Snowflake already guarantees. That test is the whole POC in a handful of statements (next-but-one slide).

Recommendation for the pipeline

1Standardise on CREATE OR REPLACE TABLE…CLONE…COPY GRANTS so consumers never lose access.
2Handle the Day-1 bootstrap: grant once after first creation, or prefer future grants. Don’t mix the two per statement.
3Reclone only after the source load commits; give the refresh role CREATE TABLE + ownership of the object so COPY GRANTS succeeds.
4Confirm no stream on the clone; set DATA_RETENTION_TIME_IN_DAYS; if Fail-safe cost matters, make the source transient (the clone inherits the type).

Other ways to refresh the consumption object

The daily reclone is the baseline; two managed alternatives, each with a caveat.

Dependent views are safe either way. A view over the clone resolves by name at query time, so it keeps working after the reclone, and the view’s own grants are untouched — only the recreated table’s grants are at stake.

How we prove it

The grant-survival test — the whole POC in a few statements

Grant, recreate with and without COPY GRANTS, and read the grants back each time.

-- Synthetic data only. Replace <…> placeholders.
GRANT SELECT ON TABLE ZONE3_CONSUME TO ROLE <reporting_role>;
SHOW GRANTS ON TABLE ZONE3_CONSUME;            -- baseline: SELECT present

-- A) WITH COPY GRANTS  →  the grant must SURVIVE
CREATE OR REPLACE TABLE ZONE3_CONSUME CLONE ZONE3_INTERMITTENT COPY GRANTS;
SHOW GRANTS ON TABLE ZONE3_CONSUME;            -- expect: SELECT STILL there

-- B) WITHOUT COPY GRANTS  →  the grant must be LOST (the failure mode)
CREATE OR REPLACE TABLE ZONE3_CONSUME CLONE ZONE3_INTERMITTENT;
SHOW GRANTS ON TABLE ZONE3_CONSUME;            -- expect: only OWNERSHIP; SELECT GONE
#RunExpected on SHOW GRANTS
ARecreate with COPY GRANTSPreserved reporting role’s SELECT still present
BRecreate without COPY GRANTSLost only OWNERSHIP remains — SELECT gone

Run once on the LM_P2_* objects and keep the output as the evidence note — that is the one thing that turns this analysis into a proven POC, in the style of the S3v2 / POC02 packs.
