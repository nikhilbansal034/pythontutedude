History Load — Chunk Planner

A script that looks at every Iceberg table in a schema and decides, for each one, how many chunks to load it in, which column divides them, how big each chunk is, and where each chunk starts and ends. It writes that plan to two metadata tables. It does not load any data.

1 / 13

One statement per table is too blunt for years of history

Why each Iceberg table needs its own load plan before anything is moved

01
Some tables are very large

Years of history per table. Loaded in one statement, a failure near the end redoes all of it.

02
Volume is not spread evenly

A bulk backfill can land most of a table's history on a handful of days. Calendar-sized chunks would be wildly uneven. Expected; confirmed by reconnaissance.

03
Tables are not all alike

CURRENT tables change in place and partition by date; HISTORY tables are append-only and partition by year / month / day.

04
Too many tables to tune by hand

The history load spans hundreds of databases with many tables each. The decision has to be made by rule, per table, automatically.

05
No stored procedures

A client constraint. Logic must run as an anonymous Snowflake Scripting block, from a Snowflake Workspace.

06
Loading is someone else's job

The plan has to stand on its own: what to load, in which pieces, with exact ranges — and nothing about how to load it.

07
Bad plans fail silently

A range that misses a row, or counts one twice, would not show up until reconciliation after the load. The plan must be provably exact.

THE ANSWER
A planner that writes an exact chunk plan per table

Read each table's structure, choose the column that splits it best, cut whole days into ~10 GB chunks, split only the days that are too big — and record every chunk's range so that each row lands in exactly one chunk.

Card 04: scale from the History Load design deck (~250 databases × ~100 tables). Card 02 is an expectation, to be confirmed by the reconnaissance in the open items.

The planner turns "load this table" into an exact, auditable list of bounded pieces

Step 1 — the table's own structure picks the dividing column

Same rules for every table; the first one that matches wins

#RuleWhy it sits here
0Small tableSplitting a table that fits in one chunk only adds overhead
1–2Partition specRead from SHOW ICEBERG TABLES. Whole partition days map exactly to files — guaranteed skipping. Both reference DDLs land here
3Naming fallbackIf the spec column is not readable in the account, the standard GRS_PROCESS_* names still identify the axis; recorded as PARTITION_VERIFIED = FALSE
4WatermarkFor a table in another schema that is not date-partitioned
5Record idAlways splits evenly, but every chunk reads the whole table
6Nothing usableFails cleanly: the reason is written, the next table is planned D6
Never used: business dates and keys (names vary, some change in place) and anything stored as a string (CHANGE_SEQ_NUM, AR_H_TIMESTAMP, GRS_LANDING_DATE).
No table is hand-tuned — the partition spec decides, with a fallback for anything non-standard
6 / 13

Step 2 — group whole days, split only the days that are too big

Two tables from the test kit, cut with a 1,000-row target (production: 10 GB)

Illustrative, not to scale — bar heights only show which days are under or over the target. Exact boundaries for both tables are in sql/TEST_PLAN.md, computed by hand and confirmed by an independent simulation.

#RuleWhat the planner does
1Group whole daysWalk the days in order; add a day to the open chunk unless it would push it over the target. The very first chunk starts open (NULL)
2Split by timestampA day bigger than the target is cut by minute ranges of GRS_REFINED_TIMESTAMP — still reading only that day's files
3Continue seamlesslyThe next range starts the day after the split day, so empty days in between are covered too. The very last chunk ends open
4Split by hashIf NULLs or one oversized minute block the timestamp split, the day is cut into even buckets of GRS_UNIQUE_ID — always works
Ranges are half-open and continuous — every row lands in exactly one chunk, by construction and by check
7 / 13

10 GB per chunk, and the technique that reads the least

One size target for every table; the technique is chosen day by day, best first

Why 10 GB (Medium-warehouse assumption) D14

ForcePushes towardsHow 10 GB sits
Keep every thread busy (Medium = 32 threads, one file each at a time)BiggerIceberg files are 16–128 MB → 80–640 files ≈ 300 MB per thread
Fixed cost per chunkBiggerSeconds of overhead against minutes of work
Cost of a failureSmallerAt most 10 GB re-read
Very narrow, compressible tablesA row cap250M rows caps them

Per table: target rows = 10 GB ÷ average row size, capped at 250M — wide tables get fewer rows per chunk, so chunks come out similar in size. Reasoned, not measured; both values are script variables.

Technique ranking

#TechniqueEach chunk reads
1Whole partition days DefaultOnly its own days' files
2Day + refined-timestamp rangeOnly that day's files
3Day + hash bucketThat day's files, once per bucket
4Refined-timestamp days, unpartitioned tableDepends on file layout
5Whole-table hash Last resortThe whole table, every chunk
One table can mix ranks 1–3. Most days grouped whole; one backfill day split. The planner always uses the best technique the table's structure and data allow.
Same target everywhere, different cut per table — driven by each table's own data, never by hand

Example of row 1. Input 'T01_CUR_SPREAD, T99_DOES_NOT_EXIST, t09_standard_table' → two VALIDATION_FAILED rows and "2 of 3 table names are invalid. Nothing was written." T01 is valid but is not planned either — a typo cannot silently drop a table.
Name matching. Exact name first, then a case-insensitive match only if it is unique. Never LIKE — _ is a wildcard and these names are full of underscores. Quote a name for an exact-case match.

What is settled

Eight design choices, and what each was chosen over

#AreaChosenOver
1Chunk columnThe table's partition spec, with a GRS fallback ladder"The single date column" heuristic of the original design — most tables have several
2Chunk shapeWhole days, splitting only oversized daysCalendar months with month→day recursion
3BoundariesHalf-open, open-ended, typed (DATE / TIMESTAMP_TZ)BETWEEN on observed min/max in a VARIANT column — gaps, overlaps, time-zone drift
4Re-planningNew plan ID; old plan superseded, never editedMERGE on chunk sequence — could rewrite chunks already used
5Chunk sizeFixed 10 GB / 250M rows10M rows (original) · detecting the warehouse (out of scope)
6MetadataTwo tables, status per tableFour tables with run log and config
7Input errorsValidate everything, exit, write nothingPlan the valid names and report the rest
8ExecutionAnonymous block from a WorkspaceStored procedure (not allowed) · Task · IDMC (deferred)
What these rest on. All tables follow the reference DDL structure · identity partitions · the loader reads the plan and writes its own SQL · the size target is a reasoned starting value.
Not settled. The final metadata location (test_db.test_schema for now, D3) and the real-data shape of history tables — both on the next slide.
Every choice that could silently lose or duplicate a row was replaced by one that cannot
