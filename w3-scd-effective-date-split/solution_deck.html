Solution Design

Three mapping tasks in one taskflow, every one pushed down into Snowflake. Step 2 runs before Step 3.

Zone1 Table 1

SCD2 — keeps history

Zone1 Table 2

SCD2 — keeps history

STEP 1 — one mapping, SQL override in the Source transformation

Rebuilds the timeline for every changed key, then diffs it against what is already in the target

STAGE table — truncate and reload

every row carries action_flag 'I' or 'D'

STEP 2 — action_flag 'D'

Target operation Update. Sets is_del = 'Y' on the rows that are no longer valid

STEP 3 — action_flag 'I'

Target operation Insert. Writes the new versions into the Zone2 target

Why two write steps rather than one MERGE: on Day 2 the target row for 10-Sep matches both a 'D' row and an 'I' row, and Snowflake errors on a non-deterministic merge by default. Splitting them removes the whole problem. Step 2 and Step 3 both need the Create Temporary View session property for pushdown to work with an update operation.

Exp date is the next date along

6 · Fill each interval

Left join both sources. Each interval matches 0 or 1 version per table, so nothing fans out

Rows already there for those keys, where is_del is 'N'

3 rows

8 · Diff the two

New not in target is 'I'. Target not in new is 'D'. Identical is left alone

4 I, 2 D

Stage 2 is the one that is easy to miss. Table 1 did not change on Day 2, but its full history still has to be pulled, or the rebuilt timeline would be missing its values. Stage 3 is what stops a change in a column we do not carry from splitting the target into two identical rows.

Open questions

QuestionWhy it matters
Reading a table from the current bucket, do we get one row per business_key, or all its versions?If we get all versions, current-bucket tables can cause this problem too, and two silent failures come with them
Can a source delete one of its own versions, or does it only add and correct?We spot changes by looking for rows whose timestamp moved. A deleted row has no timestamp, so nothing flags it and the target quietly keeps stale rows
Zone1 has SCD2 tables built from sources that overwrite in place. Do we let them drive target dates?Their dates say when we loaded the row, not when the change happened. Letting them drive gives a timeline that is neither, and no query can fix it later
Which layer does this problem sit in?Decides which engine runs the SQL, whether push-down applies, and which team owns the build
The third one changed from a question into a decision — the team has confirmed those tables exist in Zone1. Either we accept the mixed timeline and document it, or we bar those tables from setting dates and use them for values only.
