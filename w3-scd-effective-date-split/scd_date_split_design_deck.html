When two SCD2 sources load one SCD2 target

Neither source alone can determine the target's effective dates. The target's timeline has to be derived from the union of both sources' version boundaries — and rows already loaded have to be reconciled when a later run splits an interval that was already written.

Scope  Zone1 → Zone2, Snowflake only, no stored procedures
Rules  18-row decision table, Requirement.xlsx confirmed with leadership
Audience  Internal — delivery team and technical leads

The problem: one source moves, the other's rows still have to move

A target interval is only valid where it falls inside exactly one version of every source

#BoundaryComes fromEffect on the target
12026-08-10SRC_1 only Opens the first target interval
22026-08-21SRC_1 only Cuts the target even though SRC_2 did not change
Now let SRC_2 split and SRC_1 stay untouched. Every SRC_1-derived target row still has to be cut again, because the interval it occupies is no longer inside a single SRC_2 version. Neither source can be made the driver.

Why the established pattern does not apply

EstablishedHere
One driving table sets the target dates No driver exists — both sources set dates
Others LEFT JOINed purely to enrich attributes Both sources are SCD2 and both carry their own history
A row is written once per driving version A row may be re-cut by a later run that splits it

Confirmed on the 2026-09-18 walkthrough and the 2026-09-23 session with Nidwika and Ramneek.

Neither source can drive the load — the target timeline is the union of both sources' boundaries, so a change in one re-cuts rows derived from the other.

The 18 rules — the decision, then the table

The matched row's current expiry decides first; the hash only decides inside the high-end-date branch

Order matters. A row closed with a real date was published downstream, so changing it is a correction — retire and keep it visible. A row at the high end date never committed to an end, so closing it is the natural progression — expire it in place.

3 / 8

The 18 rules — grouped by branch

The same table, arranged as the four things that can actually differ — alternate to slide 3

BRANCH 1 — NOTHING DIFFERS
Rules 1 · 2 · 3 · 4

Hash same, expiry same. The rebuilt interval is already in the target exactly as derived, so there is nothing to write. Rules 2 and 4 are the rerun twins and restamp the UUID only. These are the do-nothing rules — they emit no stage row at all.

BRANCH 2 — ONLY THE EXPIRY MOVED
Rules 5 · 6 · 7 · 8

Hash same, expiry differs. At 9999 → rules 5/6 expire in place: the surrogate key survives, nothing is retired, and a new version is inserted at the new effective date if the source supplies one. At a real date → rules 7/8 retire and re-insert at the same effective date.

BRANCH 3 — ONLY THE VALUE MOVED
Rules 9 · 10 · 11 · 12

Hash differs, expiry same — a source restated a row in place. Dates alone cannot see this, and a date-only comparison would leave the stale value in the target and report success. At 9999 → dead record. At a real date → delete indicator. Both re-insert at the same effective date.

BRANCH 4 — BOTH MOVED
Rules 13 · 14 · 15 · 16

Hash and expiry both differ. Same retirement choice as branch 3, decided the same way by the expiry the row already carries: 9999 → dead record, real date → delete indicator.

RULE 17 — NO TARGET ROW AT THAT EFFECTIVE DATE

Insert. Fires for every genuinely new interval, and also at the next boundary after a rule 5/6 expire-in-place. It has no rerun twin: "there is no row to match" is the same fact on a first run and on a rerun.

RULE 18 — TARGET EFFECTIVE DATE GONE FROM THE TIMELINE

No action, deliberately. The row is left live rather than retired, because a source that has stopped reporting an interval is not the same statement as that interval never having been true.

Grouping is presentational only — the authoritative form is the 18-row table on slide 3. Keep whichever of the two reads better for the audience and delete the other.

Four things can differ, and in every branch the expiry the row already carries decides how it is retired.

Two ways a row is retired, and the expiry decides which

The single most misreadable part of the design — the two mechanisms are not interchangeable

The row being retiredMechanismWhat changesWhy
Expiry is 9999-12-31 Dead record ROW_EXP_DTE pulled back to that row's own ROW_EFF_DTE The row never committed to an end date — it meant "current, end unknown". Nothing was published to contradict.
Expiry is a real date Delete indicator IS_DEL = 'Y', both dates left alone "Valid 10-Sep to 21-Sep" went out as a report. Changing it is a correction, so the old row stays visible for traceability.
A dead record keeps IS_DEL = 'N'. So a consumer reading the target cannot filter on IS_DEL alone. The live read is IS_DEL = 'N' AND row_eff_dte < row_exp_dte — the second condition is what excludes dead records.

Getting this backwards is silent: the row count stays right, the dates look plausible, and a zero-width row simply disappears from every as-of query without anything reporting an error.

Which mechanism applies is decided by the expiry the row already carries — never by what changed about it.

Architecture — two steps, one MERGE, no procedural code

Step 1 is a view, Step 2 is a single MERGE; the stage between them is the only new object

#ArrowWhat happensOwner
1SOR → Zone1 history Zone1 builds SCD2 history for both sources. Its row_eff_dte records when Zone1 loaded the row, not when the business fact changed.Zone1
2Zone1 → Step 1 view The view reads both source history tables in full for every impacted key — not just the rows that moved in this window.This design
3view → stage The view's output is an instruction list, not target rows: a retire-plus-insert emits two stage rows.This design
4stage → target One MERGE applies every instruction atomically.This design

Constraints this design is built to

Snowflake only One MERGE No stored procedures IDMC deferred

  • Separate UPDATE then INSERT is not approved by the client — hence one MERGE.
  • Stored procedures are not allowed, so Step 1 has to be a view.
  • The stage adds exactly one column, ACTION_FLAG. Whether the real stage already has a CDC/operation column is still open — if it does, no schema change at all.
One MERGE and a view — the only new object between Zone1 and the target is a stage table carrying an instruction list.
6 / 8

How a run works — rebuild and diff, never patch in place

A run reconstructs each impacted key's whole timeline from both sources, then diffs it against the target

#StepDetail that matters
1Impacted keys Detected on process time (GRS_REFINED_TIMESTAMP), not business time. A key is impacted if either source moved.
2Boundary union This is the heart of it. The target can only be cut where some source changes, so the cut set is the union of both sources' dates.
3Rebuild Adjacent intervals with the same value collapse — but only if they actually touch. A gap keeps them separate even when the value is identical.
#StepDetail that matters
4Classify Each rebuilt interval is compared to the target row at the same effective date, producing one rule number per interval.
5Stage An instruction list, not a picture of the target. Rules 7–16 emit a 'D' and an 'I' for one interval.
6MERGE Three branches — expire in place, retire, insert — in one statement, so a run cannot half-apply.
Two clocks, never mixed. Process time (GRS_REFINED_TIMESTAMP, the sourcing window, audit columns) decides which keys a run touches. Business time (ROW_EFF_DTE / ROW_EXP_DTE) decides what the intervals are. A run never uses one in place of the other.
Every run rebuilds each impacted key's whole timeline and diffs it — so a run that changes nothing writes nothing, and re-running is free.

Worked example — SRC_2 splits, SRC_1 does not move

Two consecutive runs on one broker key, showing exactly which target rows are rewritten and why

What run 2 writes, and under which rule

IntervalWasNowRuleAction
08-10 → 08-15part of A1+B1 to 08-21 A1+B1, closed early7 retire + insert at the same eff date
08-15 → 08-21— did not exist A1+B217insert
08-21 → 08-22A2+B1 to 9999 A2+B213 dead record + insert — hash and expiry both moved
08-22 → 9999— did not exist A2+B317insert

Six stage rows for four intervals — the two retirements each emit a 'D' and an 'I'. One MERGE applies all six.

SRC_1 was not touched in run 2. Its timestamps did not move and its rows are byte-identical. Yet both of its target rows are rewritten — because the intervals they occupied are no longer inside a single SRC_2 version.
Note the two different retirements in one run. The 08-10 row sat at a real expiry, so rule 7 retires it by delete indicator. The 08-21 row sat at 9999, so rule 13 makes it a dead record. Same run, same key, different mechanism — decided purely by the expiry each row already carried.
One source moving rewrites the other source's rows — and a single run can retire two rows by two different mechanisms, because each row's own expiry decides.
