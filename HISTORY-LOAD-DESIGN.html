The new pipeline cannot deliver the old data

Why a second pipeline had to be built rather than reusing Zone 1

01
History was never loaded

Zone 2 was built incremental-first — history was "a little complicated and we never knew how to do it". Dev ran incremental and caught up later.

02
At go-live the order flips

Production must load history first, then switch to incremental. It is the only sequence that leaves the tables correct.

03
Zone 1 cannot supply it

An endpoint sources from the system of record or from Teradata, not both. And "we cannot go and mess their pipeline to inject our data".

04
Its processing adds nothing

Pre-landing, landing, raw, cast-to-defined, schema drift. Teradata data is already clean and conformed — those stages "do not add any value".

05
Scale rules out hand-work

~250–256 databases at ~100 tables each; some 800–900. Loading by hand or through Liquibase "is not a viable option".

06
The load takes days

Teradata keeps writing throughout. Whatever it writes during the load is missed — that gap is the catch-up load.

07
Teradata is not switched off

A four-to-six month parallel run follows go-live, comparing Teradata reports against Snowflake reports. Both systems keep loading.

THE ANSWER
A second, parallel pipeline

Land Teradata history in the same shape Zone 1 would have delivered it — then let the existing Zone 2 logic load it exactly as if it had come from Zone 1.

Same destination, different tap — history comes from Teradata, everything after comes from Zone 1

How it gets invoked

Three orchestration options were compared; option 3 was chosen

#OptionShapeProsConsVerdict
1LambdaMultiple Stonebranch taskflows → a Lambda on the D-migrator EC2 → D-migratorOne orchestration method. No elevated access neededTwo jobs per database per load type. More to build, configure and invoke. Manual monitoringNo
2DirectStonebranch invokes the Python script directlyOne orchestration method. No elevated accessDepends on Stonebranch supporting direct Python invocation with input variables — unconfirmedNo
3Master scriptOne master Python script runs D-migrator instances both in parallel and in sequenceLess effort to build, configure and invoke. Logs generated on EC2 with execution and failure detail. Easy to troubleshootNeeds elevated access to run the script on the EC2 consoleChosen

The design goal behind option 3

  • Execute D-migrator by parameter, parallel and sequential
  • No instance may be impacted, stopped, failed or paused because another instance failed
  • The script writes two output files on EC2 — one listing successful instances, one listing failures
  • Log file per run: log_file_name_<batchid>_<load_type>

What it is invoked with

  • Two parameters only: batch_id and load_type
  • Everything else is read from the config table
  • Zone 1 batches are at database level — 256 databases means 256 batches, doubled for history and catch-up
Open dependency. Option 3 needs elevated access to execute on the EC2 console. Aligned with LM to work with the DevOps team for admin privilege — not yet in place.
One master script drives everything; the access it needs is still being arranged

  • Stonebranch invokes with batch_id + load_type
  • D-migrator pulls every row for that pair where is_active='Y'
  • Rows are processed sequentially, one chunk at a time
  • A failure tags process_flag='N' and moves on — it does not stop the batch

The output config table, and how counts roll up

Chunk-level truth; the ABC tables are derived from it, never the other way round

Output config columns

#ColumnMeaning

4source_row_count · target_row_countThe recon numbers for this chunk
5recon_flagY only if every column reconciles and the count matches
6process_flagY if the Snowflake load itself succeeded

The roll-up rules

  • 1 — one output row per input chunk, created if absent. Re-runs update in place
  • 2 — counts summed across every chunk of a job. Status Y only if all chunks are Y
  • 3 — batch closes as completed only if every job completed

Watermark columns

The one piece of per-table analysis that cannot be automated — and it is still outstanding

#PointDetail

2Why chunk at allRunning millions or billions of rows in one go risks network failure — and in practice loading in pieces finishes faster than one shot
3What qualifiesMust be a date, and must order the records. Uniqueness alone is not enough — a random unique value such as a UUID does not qualify

What having one changes

#CaseBehaviour in the Iceberg layer

16 / 31

Nothing self-heals — recovery is two config levers and a human

A failed chunk is flagged and the batch continues; the fix is then deliberate and manual

The two levers

#ColumnDecides
1is_activeWhich chunks re-run. Set to N on every chunk you are not replaying, for that batch and job
2load_fromFrom where. 1 re-runs from Teradata; 2 skips the extract and re-runs only S3 landing → Iceberg
Step 3 is the one that bites. A reconciliation mismatch means data did land. It must be deleted from the Iceberg table — by table and watermark range — before the chunk can be replayed, or the replay doubles it.

On re-trigger

  • Every chunk still tagged is_active='Y' is picked up and re-executed one by one
  • Output config and job_run_stats rows are updated in place, not re-inserted
  • Counts are recalculated across all chunks for the table

What it needs from LM

  • There is no front end. Every step above is done by hand
  • A few named people get elevated production access for the history and catch-up window — not the whole team
  • Two permissions: DML on the config table's is_active, and delete rights on the Iceberg table
A failed chunk never stops the batch — it is flagged, and picked up deliberately afterwards
17 / 31

History and catch-up read one date pair, not one per table

The neatest idea in the design — and the reason a whole ABC table is skipped

#Loadsourcing_startsourcing_end
1History1900-01-01Max grs_refined_ts across all tables in the batch
2Catch-upThe previous successfully completed sourcing_endMax grs_refined_ts across all tables in the batch
3First incrementalEnd of the last catch-up, backed off two days in the exampleZone 1 batch end time
Why it works. The go-live cut and the load-finish are hard stop points — identical for every table in the batch. So the per-table lookup has nothing to say, and is skipped until the first incremental run.
The linchpin is grs_refined_ts — the UTC timestamp D-migrator stamps on every row. It is what lets Zone 2 slice the Iceberg table by load window rather than by business dates. Jobs finish at staggered times; the max across them becomes the window end.
One constant date pair for the whole batch — the dynamic window table comes back at first incremental

How Zone 2 runs for history and catch-up

  • Manual entry into batch_run_stats with batch_rerun_flag = H or C
  • When the job triggers, batch pre-load is skipped — the entry already exists — and job pre-load runs
  • Job entries are created as Started; jobs execute in load order
  • Execution is driven from the batch sourcing dates, passed as parameters per job
  • Post-load loads the counts and calculates the balancing flag; the batch closes when all jobs succeed
One N in the grid is the entire sourcing-window decision

When the two tables match

Scenario 1 — static and 1:1 tables share a structure but behave differently

The two sub-cases

#TypeBehaviour
1Static tablesLoaded only in the history load, never in catch-up. "Executed once in the entire lifetime"
21:1 tablesLoaded in history and catch-up — with a WHERE clause on the sourcing window, and the config SQL changed to merge rather than SQL-override
Why the merge matters. Without it, a catch-up run reloads records that are already in the target. The WHERE clause limits the window; the merge decides what to do with what comes through it.

Definition. "Same structure" means the target columns match apart from audit columns. A static table is one that is loaded once and never changes; a 1:1 table shares the structure but keeps receiving data.

What runs alongside the load

#CheckHow it is wired
1Null key DQ checkNew config column holds the query; passed into the post-session, violations to the error table
2RI checkNew config column holds the query; violations pushed to the RI link table
3Balrecon on amount columnsBetween Zone 1 and Zone 2. Loads a temp balrecon table, then the balrecon table
4ABC implementationAs per the standard wrapper
5Lineagezone1_lineage hardcoded to the literal 'HISTORICAL LOAD'
All of this is driven from the RTMI config-driven approach — the queries live in config columns, not in code, so the same framework serves every table.
The merge, not the SQL override, is what stops catch-up double-loading

Three things deliberately not built

Cases from the incremental logic that cannot arise in a history load

01
Zone 1 rerun handling

The incremental logic accounts for Zone 1 re-running and re-delivering data. In a history load there is no Zone 1 run — the data comes from Teradata. Nothing to handle.

02
Backdated entries

Same reason. Backdated entries are a Zone 1 delivery behaviour. The Teradata extract is driven by watermark ranges chosen up front, so the case does not occur.

03
Reading from the RI table

Incremental looks up Zone 1 UUIDs in the RI table. Here the lineage value is the literal 'HISTORICAL LOAD', so there is nothing to look up.

Important distinction on the third. RI violations are still written to the RI link table. What is skipped is reading from it during extraction — not the check itself.
"So these are the three things which we will not be doing — remaining everything we'll be doing."Zone 2 Design KT, session 4 — 00:53:01
Why this slide matters. It is the practical form of "history and incremental are the same design". Scenario 2 is not a new pipeline — it is the existing incremental logic with three branches removed because they are unreachable. Anything else that differs is a bug, not a design choice.
Scenario 2 is the incremental logic minus three cases that cannot arise

Type 2 target, Type 1 source — and the catch-up guard

The third scenario, and the trap that sits underneath every catch-up run

Scenario 3

The Snowflake target keeps versions; the Teradata source does not. Follows scenario 2 exactly, minus the version and hash-change calculation — the source only ever holds one version per key.

#PassBehaviour
1HistoryAll records are loaded into the target table
2Catch-upSource keys compared against target keys. Hash changed → insert a new version and expire the existing one. New key → insert. Otherwise no change

Written up in the workbook at rows 153–160. Not discussed in the KT recording.

The catch-up guard

Small Teradata tables have no watermark column, so they are truncated and fully reloaded in the Iceberg layer on every catch-up. Without a guard, Zone 2 would reprocess everything it already holds.

#OptionVerdict
1Truncate the Zone 2 and Zone 3 tables and reload themRejected "Really messy" — you must also truncate every dependent table, across hundreds of tables
2Filter: drop source records whose row_eff_dt — or watermark column where there is none — is less than the target active record's effective date. Load the restPreferred
This is the knock-on from slide 16. The decision to truncate-and-reload tables without a watermark column upstream is what creates the need for this filter downstream.
Filtering beats truncating once you count the dependent tables

Keeping the old identifiers findable

IDs the Teradata ETL invented, that the move to Snowflake would otherwise lose

#PointDetail
1The problemSome IDs in Teradata were invented by its ETL, not sourced. Move to Snowflake and they vanish — but old reports still refer to them
2ScopeOne table for all non-paid-key types, across every source system — not one per table
3Applies toOnly tables where the ETL creates an ID column and that column is part of what makes the row unique

Why Source_Table_database exists. The same Snowflake target can be fed by two different current-state databases — Teradata today, others later. The column is what keeps them apart in one shared table.
This is the third link table. Alongside the paid-ID link and the RI link. Whether paid-ID integration happens at all is still undecided — described in the KT as "controversial". The design assumes it stays until that is settled.

24 / 31

There is no single correct join

It depends on the current state and the expected output, not on a rule

#RuleDetail
1No single correct joinIt depends on the current-state structure, the data profile, and the expected output
2The acceptance testFuture-state reports must match current-state reports. So every table must join somewhere, the way it joins today
3Reverse-engineer the whole chainIf the current state passes through a view that takes only the active record before joining, and you copy just the join, you get several rows where the current state gives one
4Point-in-time joinFor master/child where the child is reference data with no standalone existence. Left join, because the child is reference type
5Window the driving table onlyWindow the child too and you may filter out the very row you need
Why the child must not be windowed. Applying the sourcing range to the child limits it to whatever arrived in that window. The child row you need may have a grs_refined_ts outside it — so the join finds nothing and you lose the entire parent record, not just the child attributes.
"If I put a sourcing window range for this child table, I'll of course limit the data… it will flush up and I will end up in not having the entire information." Zone 2 Design KT, session 4 — 01:22:16

Confirmed twice at the end of the session: this applies to regular incremental Zone 1 → Zone 2 builds too, not only to history. This topic appears in the recording only — there is no workbook sheet for it.

Window the driving table only — never the reference table it joins to

Classify PII once, at the source — everything else inherits

Where tagging sits in the run, and how a Teradata column gets its flag

Why it arises at all

D-migrator creates brand-new Iceberg tables in GRS_DIAI_RAW_HISTORY_DB. They are fresh objects carrying PII columns copied straight from Teradata. Until they are tagged, that PII sits in Snowflake untagged and unmasked — so tagging is the gate before access is granted.

#PointDetail
1Where it sits in the runStep 11 of 12 — after the Iceberg load completes, before CATE validation and before Zone 2 starts

3Why manual"Current D-migrator code does not do PII tagging". The alternative is to leverage the Zone 1 scripts if the number of PII columns in production turns out to be large
