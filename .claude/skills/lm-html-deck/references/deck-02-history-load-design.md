# Deck 2 — History Load Design

Source file: `reference docs/HISTORY-LOAD-DESIGN.html` (31 slides, single self-contained HTML file). Built to document a data-migration pipeline design (Teradata → Snowflake history load) reconstructed from a 16-sheet design workbook, a KT recording transcript, and an email thread — but again, the *structure* below is what to reuse, not the pipeline-specific content.

This is the most diagram-heavy and most mature deck on file so far — read it in full before building anything architecture-heavy. It shares deck 1's brand palette and shell mechanics almost exactly, but pushes much further on **diagrams as the primary explanatory device** (deck 1 leaned on tables and cards; this deck leans on a disciplined SVG diagram vocabulary reused across nearly every slide) and on **source-provenance discipline** (which sheet/cell/timestamp every claim traces to).

Three embedded screenshot images (`<img>` with a base64 data URI) live in this file at very long single lines — if you ever need to re-read the raw file, strip those lines first (they're each 50,000–170,000 characters and will blow a context budget) rather than reading the file whole.

## 1. What's different from deck 1's shell

Same fixed 1280×720 stage, same `fitStage`/`fitContent` engine, same "exclude certain elements from the scalable inner wrapper" trick — but extended:

- The exclusion list is now **three** classes, not two: `.takeaway`, `.slide-no`, **and `.intflag`** (see internal-slide flagging below). Any future deck that adds its own new fixed-position per-slide badge should add it to this same exclusion list.
- The sidebar (`.sidenav`) is `position:fixed`, not a flex sibling, with the deck offset by `margin-left:var(--navw)`. `fitStage` measures `nav.offsetWidth` at runtime rather than assuming a constant — slightly more robust if the sidebar's width ever changes responsively.
- **No digit-key slide jump.** With 31 slides, single-digit shortcuts (1–9) stopped being useful, so this deck dropped them and kept only arrow keys (including `ArrowUp`/`ArrowDown` as aliases for prev/next, not just Left/Right) plus Home/End. Bring back digit-jump only for short decks; drop it once a deck exceeds ~9 slides.
- **Explicit graceful degradation.** A code comment states the no-JS fallback intentionally: without JavaScript, `.slide` elements are just normal block boxes (`min-height`, a bottom margin) that stack and let the page scroll — nothing hides. Only `body.js .slide{display:none}` (added by the script) switches into the one-slide-at-a-time mode. This means the deck is fully readable — headings, tables, diagrams, all of it — even if JS fails to run, without relying on the print stylesheet. Carry this forward deliberately: don't let a future deck's shell depend on JS to be *readable*, only to be *paginated*.

## 2. Left sidebar — a second visual treatment

Same structural idea as deck 1 (fixed-width, grouped under section labels, selected-state accent), but a different skin and one new feature:

- **Full-height dark navy background** (`--navy`) rather than deck 1's white sidebar — the same brand palette, applied as a dark surface instead of a light one. Either is legitimate; pick per how much visual weight the nav should carry.
- **Brand block carries a two-line subtitle**, not just a name: `<b>History Load</b><span>GRS Teradata → Snowflake<br>Design · 31 slides</span>` — states the specific pipeline/scope *and* the slide count together, so a reader knows the deck's size before navigating.
- **An inline "INT" badge on individual nav rows** (`<span class="int">INT</span>`) for any slide flagged internal (see below) — visible in the sidebar itself, not only once you land on the slide.
- **No agenda panel duplicated onto the cover slide.** Deck 1 mirrored the sidebar's section grouping into a boxed agenda panel on slide 1, because its top-tab-bar-adjacent-nav (in that case, a persistent sidebar too, so actually the same situation) needed a linear read of the shape. This deck's cover is plain — eyebrow, H1, rule, lede, metadata block, nothing else. **Take from this: an agenda panel is worth adding to the cover only when it earns its keep beyond what the always-visible sidebar already shows** — e.g., when the deck will be printed/exported to PDF and the reader loses the sidebar, or when the cover needs to stand alone (shared as a single image, quoted in an email). If the sidebar is always present and the deck is only ever read in-browser, a separate agenda panel is redundant weight, not a requirement.

## 3. The diagram vocabulary — the main thing to take from this deck

Nearly every slide in the second half of this deck used a hand-authored inline SVG built from a small, disciplined set of reusable primitives (CSS classes prefixed `svg.dg .*`). Learn this vocabulary — it's what makes very different diagrams (a timeline, a swimlane architecture, a decision flowchart, a rollup hierarchy, a before/after comparison) all feel like they belong to the same deck instead of like ad hoc drawings.

| Class | Use |
|---|---|
| `.lane` / `.laneh` / `.lanet` | A swimlane's body / its header band / its label text — for diagrams organized as parallel tracks (by owner, by hop, by system) |
| `.box` / `.box.alt` / `.box.grey` / `.box.warnb` | Four fill states for a node: default (white, teal outline), alt (light teal tint — "the interesting/active one"), grey ("inert" or "not ours"), warnb (pale amber — "this is where risk/change/manual-attention lives") |
| `.band` | A dashed teal outline, used for a **binding, not a data flow** (e.g., a table bound to a storage location — related, but nothing flows through the arrow) |
| `.t` / `.t.s` / `.t.w` | Node label text: normal weight, a smaller secondary/detail line, or an amber warning-colored line |
| `.arw` / `.arw.d` | A solid navy arrow (real data flow, solid marker) vs. a dashed grey arrow with a grey marker (a softer/indirect relationship) |
| `.nb` / `.nt` | A small filled circle with a number inside it — the numbered step badge, used to key every arrow or node to a companion table row |
| `.brk` | A thin bracket/underline path, used to group a span of boxes under one label (e.g., "hop 1" spanning five boxes) |

**The single most important pattern in this deck: every non-trivial diagram is paired with a companion table that walks through its numbered badges one at a time** — columns like `# / Arrow / What happens / Owner`, or `# / Step / Detail`. The diagram shows the *shape* of the mechanism; the table gives each numbered step the sentence it needs. Neither replaces the other — a diagram with no companion table leaves the reader guessing what each arrow means beyond its label; a table with no diagram loses the reader's sense of the overall shape. Build both, always, for any diagram with more than 2-3 steps.

### Diagram archetypes seen, and when to reach for each

- **Timeline** (slide 4) — phases laid out left to right along a time axis, hard-stop vertical lines with dates, a bracket grouping which source owns which span. Caption explicitly if widths aren't to scale ("Phase widths are illustrative, not to scale") so a reader doesn't misread relative duration.
- **Swimlane architecture** (slide 5) — the deck's richest diagram: parallel ownership tracks, boxes colored by state, a dashed "binding" link distinct from real data-flow arrows, numbered badges on every hop, a small in-diagram legend (a tiny colored swatch box + caption text placed directly in the SVG) when box color alone needs decoding.
- **Redraw-with-subtraction** (slide 6) — take an already-established diagram and redraw it with one component removed, captioned "the same X, redrawn without Y." Communicates a state transition (before/after, or "what changes at cutover") by literal visual continuity rather than a fresh unrelated picture.
- **Stacked before/after comparison** (slide 7) — two near-identical diagrams stacked vertically, differing in only a few boxes' color/label (e.g., who owns each hop), so the *difference* is what jumps out, not the overall shape (which is deliberately kept identical).
- **Provenance/evolution timeline** (slide 8, flagged internal) — a horizontal sequence of small labelled boxes, one per draft/version of a document or design, warn-colored text marking exactly what changed at each step, a filled vs. hollow marker distinguishing "current" from "superseded." Use this when you need to show *how the design arrived where it is* across multiple source revisions — valuable as an internal audit trail, not usually external-facing content.
- **Rollup/aggregation hierarchy** (slide 14) — horizontal bands stacked vertically, each band one level of granularity (chunk → job → batch), connected by vertical arrows, paired with a short numbered rule list rather than a full table when each rule is a one-liner.
- **Decision flowchart with real branching** (slide 17) — the one genuinely non-linear diagram: a box splits into two conditional paths, each path does different things, both reconverge. Reach for this only when the underlying logic actually branches on a condition — don't force a linear process into flowchart shape just for visual variety.
- **Side-by-side regime comparison inside one figure** (slide 18) — two panels with the same internal structure, separated by a vertical dashed divider, contrasting two ways the same kind of thing is computed (a per-item lookup vs. one shared constant). Prefer this over two separate HTML-level diagrams when the two regimes share enough visual structure that overlaying them in one figure makes the contrast legible at a glance.
- **Nested "zoom into one step" inset** (slide 21) — a linear step diagram across the top, then a second, larger sub-diagram below it magnifying just one of those numbered steps (labelled "STEP 5 IN DETAIL"), because that one step's internal logic (a hash comparison with two outcomes) needed more room than the other steps. Use when one step in an otherwise-uniform sequence is disproportionately complex — don't inflate every box to match it, zoom into just the one that needs it.
- **Worked-example bridge/mapping** (slide 24) — a current-state box and a future-state box side by side, both feeding into a third box below that spells out one literal row of a mapping/link table's actual column values. Good for explaining an ID-mapping or lineage table by showing one concrete row rather than describing the schema abstractly.
- **Temporal/effective-dated join** (slide 25) — parent and child version bars drawn as time-boxed rectangles on two rows, vertical arrows showing which child version a given parent version's effective date falls inside, a highlighted box below spelling out the literal join condition in words. **Directly reusable** for any future deck explaining SCD/effective-dated join logic — this is the same class of problem as this project's other history-load work, drawn as a diagram rather than only as a table of dates.

## 4. Slide-level content archetypes not in deck 1

- **Source-inventory slide** (slide 2) — a table of *inputs* (documents, threads, recordings) each with a reliability signal, plus a companion table of every source sheet/section's status (current / still-useful / superseded), using the same 4-chip vocabulary as everywhere else (`ok`/`part`/`no`) to mark reliability rather than task status. Add this near the front of any deck built by reconciling multiple, possibly-conflicting source documents — it's what lets everything after it be trusted.
- **Enumerated causal-reasons grid** (slide 3, "the problem") — numbered one-per-card reasons (not a table), grouped visually in rows of three, with the final card in the set distinguished (different border-top color, different label color) as "THE ANSWER" rather than another reason. An alternative to deck 1's comparison-table-plus-scenario-cards problem slide — reach for a numbered reasons grid when the problem is really "N separate facts add up to why," rather than a single good/bad contrast.
- **Negative-scope slide** (slide 22, "Three things deliberately not built") — a first-class slide type documenting what was *intentionally excluded* and why, distinct from "still open" (an unresolved gap). Add one of these whenever a design deliberately narrows scope from a more general existing system — it prevents a reader from later asking "why doesn't this handle X" when X was consciously ruled out, not overlooked.
- **Screenshot-as-evidence** (slides 26, 27, 28) — an actual pasted image (not a redrawn diagram) embedded via `<img>`, used specifically when the image *is* the primary evidence being cited (a literal spreadsheet cell, a literal file's column output) rather than an illustration of a mechanism. Always paired with a caption/callout stating exactly what the image proves and why it matters that it's the real artifact (e.g., "the decision lives in the workbook only as an image, invisible to any text search"). Redraw as SVG when you're explaining *how something works*; embed the real screenshot when you're proving *that something specific happened/exists*.
- **Applicability matrix** (slide 19) — rows = mechanisms, columns = contexts/scenarios, cells = `Y` / `N` / `—`. Distinct from an ID-tagged requirements table (deck 1) or a comparison table (options) — use a matrix when the real content is "which of these N things applies in which of these M situations," and then call out the one exceptional cell in prose below rather than leaving the reader to spot it themselves.
- **Column-by-column data-dictionary slide** (slides 13, 16 partially) — documents a specific database table's schema, one row per column with its meaning, alongside a narrower column of process notes. Use this whenever a config table or schema is central enough to the design that a reader needs to know what's actually in it, not just that it exists.
- **Decisions-log capstone** (slide 29, "What is settled") — a `# / Area / Chosen / Over` table walking through every major decision in the whole deck and naming what alternative it beat, not just what was picked. This is a stronger closing pattern than deck 1's plain answers table: it makes the deck's own argument re-traceable in one slide, because "chosen over X" is what actually justifies a decision, not the decision alone.
- **Source-conflicts audit** (slide 30, flagged internal) — table of every place the source material disagreed with itself (older sheet vs. current sheet), with a callout naming the consequence of trusting the wrong one. Pair with an explicit list of which source sections to skip and why their now-superseded text still has salvageable non-text content (diagrams, in this case).
- **Closure-ratio framing on the closing "open items" slide** (slide 31) — the subtitle states a concrete fraction ("Eight of sixteen tracked items remain"), and the slide itself splits into three buckets: items waiting on the client, items still internal, and — notably — items **already closed during the design process**, each with a `Done` chip. Stating progress as a ratio against a fixed original count, and explicitly listing what's already resolved (not only what's outstanding), reads as far more rigorous than an open-items list alone.
- **Quote as first-class evidence** (used throughout, not just once) — the `.quote` component (left-accented, italic, with a `<span>` attribution line giving the exact source and timestamp) is used repeatedly as primary evidence for a specific claim, often placed directly beside a `.callout` stating the rule the quote justifies. This is a step beyond deck 1's small muted citation lines — a verbatim quote lets the reader judge the source's own words, not just trust a paraphrase.

## 5. Refinements to disciplines from deck 1

- **Internal vs. external slide flagging.** Any slide meant for internal process/audit use rather than the client-facing narrative gets `class="internal"` on the `<section>`, which swaps its left accent stripe from teal to grey, adds a bottom-left `INTERNAL` badge (excluded from `fitContent` scaling, same as the takeaway bar), and shows a small `INT` pill next to its entry in the sidebar. Use this whenever a deck needs to carry meta-commentary (source provenance, conflict audits, draft history) inside the same file as the narrative meant for the client — don't split into two separate files if the two audiences overlap enough to want one navigable deck.
- **Chips are semantic states, not fixed words.** This deck reuses the same four CSS classes (`ok`/`warn`/`no`/`part`) but fills them with whatever word fits the specific claim: `Done`/`Chosen`/`Preferred` all render as `ok`; `Blocking`/`To confirm`/`Manual insert` all render as `warn`; `Rejected`/`Least attractive` render as `no`; `Undecided`/`Live` render as `part`. Pick the class by the *semantic color* the claim needs (good/caution/bad/partial), then write whatever label makes the specific claim clear — don't treat the chip vocabulary as a closed enum of exact strings to reuse verbatim.
- **Multiple callouts per slide is normal, not an exception.** Deck 1 mostly used one callout per slide; this deck freely uses two or three when a slide has that many distinct side-notes worth flagging (e.g., slide 16 has a "knock-on effect" callout and a separate "blocking" callout). Don't artificially compress multiple distinct warnings into one paragraph just to keep to "one callout" — give each its own box.
- **Not-to-scale disclosure.** Any diagram whose spatial layout could be mistaken for a scaled quantity (a timeline's phase widths, in this deck) gets an explicit caption saying so. Cheap to add, prevents a real misreading.
- **Source citations go down to the cell/line/timestamp, and state their own coverage.** Beyond "cite your source" (deck 1's discipline), this deck routinely notes *how completely* a source covers a claim — "Written up in the workbook at rows 153–160. Not discussed in the KT recording," or "Confirmed twice at the end of the session." This tells a reviewer not just where a claim came from but how much to trust it.

## 6. Visual system deltas from deck 1

Same `:root` token names and roles as deck 1 (`--navy`, `--teal` family, `--green`/`--green-ac`, `--orange`, `--red`, `--g1`…`--g11`, same system font stack, no Google Fonts, no dark mode) — this confirms the brand palette is a fixed constant across decks in this family, not something that varies by author or topic. Two small additions:

- An extra token, `--blue` / `--blue-ac` (`#00A3E0` / `#007CB0`), not present in deck 1 — available as a secondary accent if teal is already carrying too much meaning on a given slide (not used to fully replace teal in the sections read here; treat as reserved, not primary).
- Slightly smaller base measurements throughout (16px body vs. deck 1's 17px, tighter table padding via `table.sm`) — appropriate given this deck has roughly 4x as many slides and denser per-slide content; don't treat deck 1's exact pixel values as sacred, size to the deck's actual density.

## 7. What to take away for the next deck

- If the new deck is **architecture/mechanism-heavy** (a pipeline, a data flow, a state machine, a decision procedure), lean on this deck's SVG diagram vocabulary and the diagram+companion-table pairing, not deck 1's card/table-only approach.
- If the new deck is **built by reconciling multiple, possibly-conflicting source documents**, open with a source-inventory slide (§4) and consider a closing source-conflicts audit if real contradictions were found, both flagged/unflagged internal as appropriate.
- If the new deck's scope was **deliberately narrowed** from something broader, add a negative-scope slide rather than leaving the narrowing implicit.
- If the new deck needs to **prove** something (a decision really was made, an artifact really says what's claimed) rather than **explain** a mechanism, consider embedding a real screenshot instead of redrawing it — but always caption what it proves.
- Reuse the temporal/effective-dated join diagram archetype (§3) directly for any future SCD/history-load design work in this project — it's the closest match yet to that recurring problem shape.
